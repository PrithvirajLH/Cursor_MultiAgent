**Category:** Logic Error

**Issue:** The receipt is reserved before ticket/message side effects, but any later failure deletes the receipt, even after a ticket or threaded message was already persisted.  
**Impact:** Retries can create duplicate tickets, duplicate replies, and duplicate events for the same inbound email. **Root Cause:** idempotency bookkeeping is not transactional with the actual mutation work. **Fix:** wrap receipt finalization and ticket/message creation in one transaction, or retain a terminal failed receipt state instead of deleting the receipt after partial success.

**Category:** Security  
**File & Location:** [inbound-email.service.ts](/c:/Users/PHulgur/Downloads/Ticketing%20System%20Quality%20Review/apps/api/src/tickets/inbound-email.service.ts):391-491 (`downloadInboundAttachmentBuffer`, `getInboundAttachmentAllowedHosts`)  
**Issue:** When `INBOUND_EMAIL_ATTACHMENT_ALLOWED_HOSTS` is unset, any HTTPS `contentUrl` is accepted, and the fetch follows redirects by default.  
**Impact:** The webhook can be turned into an SSRF primitive against internal or sensitive network targets. **Root Cause:** the host allowlist is fail-open instead of fail-closed. **Fix:** require an explicit allowlist, reject redirects (`redirect: 'error'`) or revalidate the final URL, and prefer provider-owned blob hosts only.

**[TICKET-005]** | Severity: ?? High  
**Category:** Race Condition  
**File & Location:** [email-processor.service.ts](/c:/Users/PHulgur/Downloads/Ticketing%20System%20Quality%20Review/apps/api/src/notifications/email-processor.service.ts):51-82 (`process`); [outbox.service.ts](/c:/Users/PHulgur/Downloads/Ticketing%20System%20Quality%20Review/apps/api/src/notifications/outbox.service.ts):49-60 (`findById`, `markProcessing`)  
**Issue:** Two workers can read the same `PENDING` outbox row, both mark it `PROCESSING`, and both send the email.  
**Impact:** Duplicate customer emails and broken email-thread state. **Root Cause:** the claim step is read-then-write instead of atomic compare-and-set. **Fix:** use `updateMany(... where: { id, status: PENDING })` and proceed only when `count === 1`, or lock the row in a transaction.

**Phase 3**
- **System Design & Architecture:** Add an access-aware realtime audience service that resolves recipients from the same authorization graph used for reads/writes; this removes the current class of data leaks and makes websocket behavior auditable. **Complexity:** Hard **Priority:** Medium-term  
- **System Design & Architecture:** Move notifications/email into a transactional outbox + worker queue with explicit claim semantics and dead-letter handling; this eliminates duplicate sends and gives you recoverable delivery pipelines. **Complexity:** Medium **Priority:** Quick Win  
- **System Design & Architecture:** Introduce workspace/team isolation primitives at the data and event layers; this makes future multi-team or multi-tenant expansion safer than today’s shared group model. **Complexity:** Hard **Priority:** Long-term vision  
- **Performance:** Cache counts/search/report aggregates in Redis and invalidate them from ticket mutations; this will cut repeated expensive list/report queries. **Complexity:** Medium **Priority:** Quick Win
