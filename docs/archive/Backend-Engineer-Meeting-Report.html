1. Current Database Setup

What You Use Today

  • ORM: Prisma
  • Database: PostgreSQL (via Supabase or Docker)
  • Connection strings: DATABASE_URL and DIRECT_URL in apps/api/.env
Supabase usage: Supabase is used only as a PostgreSQL host. The README says to put your Supabase connection strings in DATABASE_URL and DIRECT_URL. There is no Supabase SDK or Supabase-specific code in the backend. Moving to another PostgreSQL (e.g. Azure, AWS RDS, self-hosted) is a connection-string change plus any infra differences.

Connection Details

  • DATABASE_URL: Used for pooled connections (e.g. Supabase pooler, PgBouncer)
  • DIRECT_URL: Used for migrations and schema operations (direct connection, no pooler)
  • Prisma binary targets: native and debian-openssl-3.0.x (for Azure App Service Linux)

Connection Retry

PrismaService retries DB connection on startup with exponential backoff:

  • DB_CONNECT_MAX_RETRIES = 8 (default)
  • DB_CONNECT_INITIAL_DELAY_MS = 500
  • DB_CONNECT_MAX_DELAY_MS = 10,000

Local Development

docker-compose.yml runs:

  • postgres: Port 5432, DB ticketing
  • postgres_test: Port 5433 (host), DB ticketing_test
  • redis: Port 6379 (for BullMQ queues when enabled)

Inbound Email Flow

  1. Webhook receives payload at POST /tickets/inbound-email
  2. Validates x-inbound-email-secret (or x-m365-inbound-secret)
  3. Idempotent via InboundEmailReceipt (messageId)
  4. Threading via In-Reply-To/References → existing ticket or new ticket
  5. Requester created/updated from fromEmail/fromName
  6. Message added; attachments normalized and stored
  7. Notifications and realtime events emitted

SLA Flow

  1. Sync: SlaEngineService.syncFromTicket() on ticket create/update
  2. Policy: Resolved from team → SlaPolicyAssignment → SlaPolicyConfig + targets
  3. Breach worker: SlaBreachService runs on interval; processes SlaInstance with nextDueAt in range
  4. At-risk/breach: Notifications to leads/on-call; automation triggers SLA_APPROACHING / SLA_BREACHED

Background Queues (Optional)

BullMQ (Redis) for email and automation when NOTIFICATIONS_QUEUE_ENABLED and AUTOMATION_QUEUE_ENABLED are true. Otherwise inline processing.

6. Auth & Security

Authentication

  • Primary: Azure AD / Entra ID (RS256 JWT via JWKS)
  • Fallback: HS256 JWT when AUTH_JWT_SECRET is set
  • Dev/test: x-user-id and x-user-email when AUTH_ALLOW_INSECURE_HEADERS=true
  • Provisioning: First login creates/updates user; AUTH_BOOTSTRAP_OWNER_EMAILS promotes to OWNER

Authorization (AccessControlService)

  • OWNER: full access
  • TEAM_ADMIN: primary team tickets
  • LEAD: team tickets
  • AGENT: assigned or unassigned team tickets
  • EMPLOYEE: own tickets only

Webhook Secrets

  • Inbound email: x-inbound-email-secret or x-m365-inbound-secret = INBOUND_EMAIL_WEBHOOK_SECRET
  • Attachment scan: x-attachment-scan-secret = ATTACHMENT_SCAN_WEBHOOK_SECRET

Rate Limiting

  • Default: 120 req/min (RATE_LIMIT_LIMIT, RATE_LIMIT_TTL_MS)
  • Webhook routes: 30 req/min
  • High-write ticket routes: 60 req/min

8. Migration Checklist (Supabase → Real DB)

Questions the Backend Engineer May Ask

  1. Connection strings: Do you use Supabase pooler? (DATABASE_URL = pooled, DIRECT_URL = direct)
  2. Schema: All 38 migrations must run cleanly on the new DB. Any custom Supabase extensions?
  3. Binary targets: Prisma generates for native + debian-openssl-3.0.x. Where will you deploy?
  4. Advisory locks: SlaBreachService uses pg_try_advisory_xact_lock for distributed locking. Works on any Postgres.
  5. Trigram indexes: Migration 20260220150000_add_ticket_search_trigram_indexes runs CREATE EXTENSION IF NOT EXISTS pg_trgm. Ensure your new Postgres allows extensions (or enable pg_trgm manually).
  6. Data migration: Export from Supabase, import to new DB. Attachments: local or Azure Blob?
  7. Seeds: SEED_MODE=minimal|test|dev. Use for initial data after migration?
  8. Test DB: .env.test uses DATABASE_URL. Use separate test DB on new infra.
