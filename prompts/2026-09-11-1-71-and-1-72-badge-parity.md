## 1 — Card 1.71: the Unassigned badge disagrees with the list it opens (XS)

### ⚠️ Read this correction first — the planner's first version of this card was wrong

**I originally wrote that the badge and the list never match. That was wrong, and
your browser measurement (badge 5, list 5) is right.** I read
`saved-views.ts:103` emitting `?scope=unassigned` with no status filter, checked
`buildListWhere:448`, and stopped there. I should have followed the request the
web app actually sends. **`useFilters.ts:42-45` is what I missed:**

```ts
const statusGroup =
  (searchParams.get("statusGroup") as StatusFilter) ||
  presetStatus ||
  undefined;
```

When the URL carries no `statusGroup`, the list falls back to `presetStatus` —
`App.tsx:539`'s `ticketPresetStatus`, which **initialises to `"open"`**. So on a
normal load the request does carry `statusGroup=open`, and badge and list agree
exactly as you measured. **The API integration test's
`scope=unassigned&statusGroup=open` is therefore a fair model of the real
request, not a fiction — I was wrong about that too.**

### What is actually wrong: the preset does not say what it means

`ticketPresetStatus` is **ambient React state**, not part of the link. Two nav
items change it (`App.tsx:734`, `:719`):

| you last clicked | `ticketPresetStatus` becomes | then click **Unassigned** in the sidebar and the list means |
|---|---|---|
| *(fresh load)* | `"open"` | unassigned **and open** — matches the badge ✅ |
| **Created by me** | `"all"` | unassigned, **any status** — badge 5, list 6 ❌ |
| **Completed** | `"resolved"` | unassigned **and resolved only** — badge 5, list 1 ❌ |

**So the agreement holds on the path you tested and breaks on two others.** It is
a latent inconsistency, not the broken-every-time defect I first described —
lower severity, same one-line fix.

✅ **And the app already disagrees with itself about this.** The left-nav's own
Unassigned item (`App.tsx:729-731`) navigates to:

```
/tickets?scope=unassigned&statusGroup=open
```

**explicitly.** The sidebar preset is the one place that leaves it implicit, so
the two routes to the same view can produce different lists.

### The fix

- [ ] **One line in `apps/web/src/components/shell/saved-views.ts`:**

      ```ts
      buildQuery: () => qs({ scope: 'unassigned', statusGroup: 'open' }),
      ```

      ✅ **Verified this is exactly equivalent.** `statusGroup=open` in
      `buildListWhere:429` is `status: { notIn: [RESOLVED, CLOSED] }` — the same
      predicate the count uses, not merely a similar one.
- [ ] **Leave `matches` alone.** `paramsMatch` is a subset check
      (`saved-views.ts:56-58`), so `{ scope: 'unassigned' }` still matches the
      wider URL and the row still highlights.
- [ ] ⚠️ **Do NOT instead widen the count back.** The owner decided open-only in
      1.70, `DashboardPage` and `getSidebarChildBadge` have shown that number for
      months, and `unassignedAnyStatus` was deleted for good reasons. **The list
      moves to meet the badge, not the other way round.**

### Tests — and this is the part that matters more than the line

- [ ] ⚠️ **A web test for the thing that actually broke: the preset's link must
      carry its own status filter.** Assert that
      `SAVED_VIEWS.find(v => v.id === 'unassigned').buildQuery()` contains

      list inherits `ticketPresetStatus`, so the same row means three different

- [ ] ⚠️ **Assert the sidebar preset and the left-nav item emit the SAME query.**

## 2 — Card 1.72: `completedAt` was never backfilled (S, one data migration)

### What is wrong

You flagged that `overdue` "has the same shape `atRisk` had". **You were right,
and the cause is older and larger than the predicate.**

`completedAt` was added by migration `20260123151500_add_completed_at`. The whole
migration is:

```sql
ALTER TABLE "Ticket" ADD COLUMN "completedAt" TIMESTAMP(3);
```

**There is no backfill.** Nothing populated it for tickets already resolved or
closed on 2026-01-23. From that day, `changeStatus`
(`tickets.service.ts:3050-3055`) sets it on RESOLVED/CLOSED and clears it on
REOPENED — so the invariant *"completedAt is set exactly when the ticket is
finished"* is true for everything touched since, **and false for everything
finished before.**

Both definitions in play rely on that invariant, and each picks a different half:

| | "finished" is expressed as |
|---|---|
| `getCounts.atRisk`, `getCounts.overdue` | `status NOT IN (RESOLVED, CLOSED)` |
| the list's `slaStatus=at_risk` / `breached` (`:548-560`) | `completedAt IS NULL` |

For a ticket resolved **before** 2026-01-23 the two answer differently: the
status says finished, the null `completedAt` says not. So a legacy resolved
ticket with a past due date **appears in the `slaStatus=breached` list and not in
the `overdue` count** — and the same holds for `at_risk`.

⚠️ **This means card 1.70's "the count and the list agree" is true for tickets
created since January and not proven for the rest.** The integration test passes
because its fixture builds fresh rows. **That is not the test's fault and it is
not 1.70's fault — the fixture cannot contain a row from before a migration.**

### ⚠️ Measure it before you fix it — I have not

The planner has **not** run this against production. **Run it first and report
the number**, because it decides whether this is a real correction or a tidy-up:

```sql
SELECT count(*) AS legacy_finished_rows,
       count(*) FILTER (WHERE "dueAt" IS NOT NULL AND "dueAt" < now()) AS would_show_as_breached
FROM "Ticket"
WHERE "completedAt" IS NULL
  AND "status" IN ('RESOLVED', 'CLOSED');
```

- [x] ✅ **MEASURED BY THE PLANNER 2026-09-11 AGAINST PRODUCTION: 427 tickets, 6 finished, 0 without the stamp, 0 that would show as breached. The answer is ZERO. Do not write the migration.** Original instruction, kept for the record: **If the first number is 0, say so and stop** — the invariant already holds
      everywhere, the divergence is theoretical, and all that is left is item ③
      below. **Do not write a migration for zero rows.**
- [ ] ⚠️ **Run it against the Supabase dev database too.** The two have different
      histories and only one of them proves anything about production.

### The fix, if there are rows

- [ ] **Migration 62 — backfill, additive, no `DROP`:**

      ```sql
      UPDATE "Ticket"
         SET "completedAt" = COALESCE("closedAt", "resolvedAt", "updatedAt")
       WHERE "completedAt" IS NULL
         AND "status" IN ('RESOLVED', 'CLOSED');
      ```

      ⚠️ **Check `closedAt` and `resolvedAt` actually exist and are populated on
      those rows before relying on them** — `updatedAt` is the fallback precisely
      because it always has a value, but it is the least accurate, so prefer the
      other two and **report how many rows fell through to it.**
- [ ] ⚠️ **Hand-check the generated migration to zero `DROP` statements.** The
      standing twelve destructive statements Prisma emits (six `DROP INDEX` on
      the trigram GIN indexes, six `ALTER COLUMN … DROP DEFAULT`) must not be in
      it. **If you did not write the file by hand, you did it wrong.**
- [ ] ⚠️ **The planner cannot run this against production** — destructive writes
      are blocked from agent sessions here. **Write it as a migration so the
      normal deploy applies it**, and apply it to **Supabase dev first**, which is
      this repo's standing order.
- [ ] ③ **Then make the two spellings one.** With the invariant true everywhere,
      pick a single expression of "finished" and use it in both places, with a
      comment saying which and why. **The planner's view: `completedAt IS NULL` is
      the better one** — it is one column rather than an enum list that grows, and
      it is already indexed (`Ticket_completedAt_idx`, migration
      `20260206153000_add_perf_indexes`). **But say which you chose.**

### Tests

- [ ] ⚠️ **A fixture row that reproduces the legacy shape** — status RESOLVED,
      `completedAt` explicitly `null`, a past `dueAt` — and an assertion that the
      `overdue` count and the `slaStatus=breached` list **both** exclude it. **This
      is the assertion the whole card is for**, because it is the one thing the
      existing fixture structurally cannot contain.
- [ ] **The same shape for `at_risk`**, with a future `dueAt` inside the window.
- [ ] **Pin both to exact numbers, not to each other.** Card 1.70's own comment
      makes this point better than I can: comparing count to list passes when both
      sides move together, which is exactly how the unassigned defect survived.
