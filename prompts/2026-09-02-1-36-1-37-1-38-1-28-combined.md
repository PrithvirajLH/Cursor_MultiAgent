## 4. Stage 1 — 1.36: a staff member's own ticket (API)

**Files:** `apps/api/src/tickets/tickets.service.ts`,
`apps/api/src/common/access-control.service.ts`

Two faults, one cause. **Land them together.**

### Fault A — a staff requester reads the internal notes about themselves

Today any non-EMPLOYEE who can open a ticket reads every internal note on it,
**including a ticket they raised**. The scenario is unavoidable: payroll is the
only department operationally receiving tickets, so a payroll lead with a problem
about her own pay has nowhere else to file, and "agents won't raise tickets to
their own department" is not available as a mitigation.

- [ ] `tickets.service.ts:1024-1027` — add "or is the requester", mirroring the
      guard card 1.22 landed on the send path:

      ```ts
      const isRequester = ticket.requesterId === user.id;
      const where: Prisma.TicketMessageWhereInput = {
        ticketId,
        ...(user.role === UserRole.EMPLOYEE || isRequester
          ? { type: MessageType.PUBLIC }
          : {}),
      };
      ```

- [ ] Confirm `ticket` (with `requesterId`) is already in scope at that point. If
      it is not, load it — do **not** re-derive the requester from anything else.
- [ ] **Do not** go looking for other read paths. §3 establishes there is one.

### Fault B — a staff member cannot see their own ticket at all

`roleFilter` gives EMPLOYEE a `requesterId` clause and gives LEAD/TEAM_ADMIN team
scope with none. So staff raising a ticket to a team they are not on cannot see
it: not in a list, not by URL, no reply, no confirmation it was resolved.

- [ ] `access-control.service.ts:40` `roleFilter` — add "or requested by me" to
      the TEAM_ADMIN, LEAD and AGENT branches, as an `OR` alongside the existing
      team scope. Rank still governs everything else.
- [ ] Leave OWNER (`{}`) and EMPLOYEE (`{ requesterId }`) alone.
- [ ] Leave the `:59-61` no-team fallback alone — it is already correct.
- [ ] **Check the SQL sibling.** `operationalTeamIds` is also used to build a raw
      team scope at `:122` (`teamScopeSql`). Establish whether that path needs the
      same requester clause to stay consistent with `roleFilter`, and **say what
      you found** — if it does and you skip it, list and detail disagree.

### Fault C — the web and the API disagree about what a team is

Observed live 2026-09-02: `phulgur@` had `primaryTeamId = payroll` but no
`TeamMember` row, so the assign control never rendered and **no request reached
the server to be refused**. Resolved in production by adding the roster row.

The API accepts a **three-tier** fallback: `memberTeamIds` → `teamId` →
`primaryTeamId` (`auth.guard.ts:118`, then `operationalTeamIds`). The web
(`TicketDetailPage.tsx:334`) implements only tier one — roster rows.

- [ ] **Make a mismatched account impossible to create silently.** Pick the
      cheaper of: the web mirrors the guard's fallback, or `primaryTeamId` stops
      being accepted as team scope without a roster row.
- [ ] Either way, **fail loudly**: log a warning (or refuse the save) when an
      account has a `primaryTeamId` with no matching `TeamMember`. Silence is what
      cost the time here.
- [ ] `memberTeamIds` is built from roster rows with **no** fallback while
      `teamId` has one, so the API is internally inconsistent too. **One
      definition, applied everywhere.** Say which you chose and why.

## 5. Stage 2 — 1.38 and 1.37: an agent can tell what they sent (web)

**Files:** `apps/web/src/pages/TicketDetailPage.tsx`,
`apps/web/src/components/ticket-detail/TicketConversation.tsx`

`curl -d '{"type":"PUBLIC"}'` → `{"type":"INTERNAL"}`, **201**.

### 5a — Believe the server, not our own intent (do this first)

Even with 5b in place the override can still fire: an agent opens an assigned
ticket, starts typing a public reply, and someone reassigns before they hit send.
This is the only thing that catches that.

The client already has the truth and uses it in one place of three:

| Line | Today |
|---|---|
| `:1432` | optimistic bubble built from local `messageType` |
| `:1452` | on success maps **only** `localStatus: "sent"` — never the type |
| `:1460` | realtime event **does** use `serverMessage.type` ✅ |
| `:1467` | toast keys off local `messageType` → "Reply sent" |

- [ ] `:1452` — also replace the optimistic message's `type` with
      `serverMessage.type`.
- [ ] `:1467` — key the toast off `serverMessage.type`, and when it differs from
      what was requested **say so**: e.g. *"Saved as an internal note — the
      requester was not emailed."* Do not silently swap the wording.

### 5b — Stop offering `Public` where the server will refuse it

Per the owner's ruling (§3): the API is right.

- [ ] `TicketDetailPage.tsx:383` — delete the `if (!ticket.assignee) return false`
      early return so the web's `isPeerAgent` matches the API's. The effect at
      `:1256` then pins `messageType` to `INTERNAL` and the composer already
      renders the "Internal note only" chip instead of the toggle.
- [ ] `TicketConversation.tsx:416-423` — the chip's `title` reads *"You can only
      leave internal notes on tickets assigned to a teammate."* **Wrong for an
      unassigned ticket.** Give that case its own wording naming the way out:
      *"Assign this ticket to yourself to reply to the requester."* The sidebar
      already has a **Me** button beside Assignee — that is the action to point
      at.
- [ ] Prefer one extra prop over recomputing ticket state inside the conversation
      component.

### 5c — Make an internal note look internal to its author

- [ ] `TicketConversation.tsx:341` — `isCurrentUser` short-circuits before
      `isInternal`, so the amber treatment is unreachable for your own notes and
      works only for other people's. Make internal-ness survive that branch:
      amber border/tint over the sent-bubble shape, or an amber ring on the blue
      bubble. **Do not simply reorder the ternary** — that makes your own notes
      look like someone else's and costs the left/right sent/received distinction
      the layout depends on.
- [ ] `:298` — the `Internal` badge sits inside the `isGroupStart` header, so a
      run of six internal notes carries **one** badge (confirmed in the browser).

- [ ] Safe per-message: the grouping predicate at `:251-255` already includes

- [ ] Leave the `PUBLIC` mount default alone. It is correct and verified

## 6. Stage 3 — 1.28: the agent can see and control who a message reaches

After 1.33 made a reply one email (`To:` requester, `Cc:` the rest) and 1.34
removed "Also copied" from the body, **the compose screen is the only place
anyone sees who a message will reach.** An agent writes something candid on a
termination ticket and it goes to three people they would have to hunt to
identify. On payroll and HR tickets that is a safety gap, not a convenience.

### 6a — The recipient preview endpoint

**Files:** `apps/api/src/tickets/tickets.controller.ts`,
`apps/api/src/notifications/notifications.service.ts`, a response type

- [ ] `GET /api/tickets/:id/message-recipients?type=PUBLIC|INTERNAL`, gated by
      the **existing** `canPostMessage` (`access-control.service.ts:228`). Do not
      invent a check.
- [ ] Expose a **public** method on `NotificationsService` that calls the private
      `buildRecipients` (`:456`) with **exactly** the `messageAdded` options from
      `:151`:
      `includeRequester: true, includeAssignee: true, includeFollowers: true, excludeUserId: <calling agent>, excludeEmployees: (type === 'INTERNAL')`
      then applies `resolveOutboundRecipients`. Return
      `{ to: {id,name}|null, cc: {id,name,removable}[], refused: {address,reason}[], emails: boolean }`,
      with `emails: false` for an internal note.
- [ ] **Names, never addresses.** This renders on a screen a requester may be
      reading over a shoulder, and 1.34 already decided names read better.
- [ ] `excludeUserId` is the **calling agent** — `messageAdded` excludes them, so
      the composer must not list the author.

### 6b — The list above the composer

**Files:** `apps/web/src/pages/TicketDetailPage.tsx`, new
`apps/web/src/components/ticket-detail/MessageAudience.tsx` + test

- [ ] One quiet line **directly above the compose box** — not the sidebar, not
      behind a disclosure. The point is that it is unavoidable while writing:
      **"Goes to Bhavesh Patel · Greg Weitzer, Dana Whitfield"**, requester first.
- [ ] Expands to a small list with an **×** per removable person. Confirm before
      unfollowing (`ConfirmDialog` exists in `components/ui/`).
- [ ] **Removal unfollows from the ticket** — not a per-message exclusion. A
      per-message list is state nobody will understand in three months and it
      silently varies the audience between messages in one thread. Use the
      existing `DELETE /:id/followers/:userId`.
- [ ] **The requester cannot be removed.** Show them as fixed; a public reply
      with no `To:` is not a thing.
- [ ] Switching to an internal note replaces the line with **"Internal note —
      staff only, no email sent."** Refetch on type change or fetch both once and
      swap — say which.
- [ ] Show refusals inline when present: *"1 address cannot be emailed"*, reason
      on hover. An agent should not discover that after sending.
- [ ] Must not shift the composer's layout when it appears or expands.
- [ ] States: loading → render **nothing** (secondary furniture, not a spinner);
      error → *"Couldn't check who this reaches"*. **Never silently show
      nothing** — absence reads as "nobody".
- [ ] **Coexist with 5c.** Both add furniture near messages. On an unassigned
      ticket an agent now sees the internal-only chip *and* "staff only, no email
      sent" — coherent, and it explains why the toggle is gone. Make sure it does
      not read as two competing warnings.

### 6c — What actually happened, per message

**Files:** `apps/api/src/tickets/tickets.service.ts`,
`apps/web/src/components/ticket-detail/*`

- [ ] Where messages are loaded (`:1029` — the same place Stage 1 touched), fetch
      the ticket's outbox rows in **one** query and attach
      `{ emailed: number, refused: number, internal: boolean }` to each message by
      `payload.messageId`. **Do not query per message.**
- [ ] Render a small muted label per message: `emailed to 3`,
      `internal — not sent`, `emailed to 2 · 1 refused`.
- [ ] **Report the outbox, not the intent.** A label saying "emailed to 3" when
      the send was refused is worse than no label, because the agent stops
      chasing.
- [ ] Since 1.33 a public message produces **one** outbox row carrying `to` and
      `cc`, so this is one query per ticket grouped in memory.

## 10. Security considerations

- **1.36 is a permissions change to a chokepoint.** `roleFilter` and the message
  filter gate every list, detail and count in the product. Widening either by
  accident is the worst outcome in this batch. The clauses you add must be
  **`requesterId === user.id`** and nothing looser — never an email comparison,
  never a name.
- **Do A and B together** (§4). B alone lets a staff requester reach a ticket
  *and* read its internal notes.
- **The preview must not become an information leak.** It answers "who would
  receive a message I am allowed to post", so it is gated by the same check as
  posting, and it must not reveal anything the followers list does not already.
- **Names, not addresses**, in the preview response (§6a).
- **Removal is a real mutation** — it changes who receives everything afterwards.
  Confirm first, and let the existing follower endpoint apply its own permission
  rules rather than adding a bypass.
- **The per-message indicator reports the outbox, not the intent** (§6c).
- Cards 1.22, 1.23 and 1.33 own the send path and are untouched here. **If a test
  of theirs goes red, stop** — nothing in this batch should reach them.
