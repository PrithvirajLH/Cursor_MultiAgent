## 1. What makes this deploy different

**Three migrations at once** — 55, 56, 57. All additive, all **0 DROPs** by hand
check, all already applied to local-dev Supabase. They must run **before** the
app.

**It fixes two defects that are live in production right now:**

- **The "Insert template" button is unclickable.** Card 1.39 made the toolbar
  render only while the editor has focus, and a mousedown on a toolbar button
  blurs the editor — so it unmounts before the click lands. Broken since the
  2026-09-03 deploy.
- **Template placeholders blank people's names.** The picker had its own copy of
  the substitution logic using different variable names from the three on-screen
  hints, so an agent following the instructions sent *"Hi ,"* to a requester.

**And it is the biggest behaviour change of the week: staff stop receiving email.**
Card 1.42 takes eleven kinds of email down to four, all to people outside the
system. Assignment, transfer, non-resolved status changes and **both SLA alerts**
stop sending. Staff keep the in-app bell for all of it.

> **⚠️ `EMAIL_TEST_RECIPIENTS` is still set, and must stay set through this
> deploy.** Every email still redirects to the owner's inbox, so **this deploy does
> not start emailing real requesters**. Clearing it is a separate, deliberate
> owner step with its own checklist on card 1.24.

## 4. Deploy — migrations first

Follow `docs/DEPLOYMENT.md`, and read **Gotcha 0** first: writing to Azure needs a
Conditional Access token and the failure does not say so.

### Step 1 — Record where production is

```bash
az webapp config appsettings list -g csnhc-ai -n TicketTicket \
  --query "[?name=='DEPLOYED_COMMIT_SHA'].value | [0]" -o tsv     # expect 1b5e8f5

PROD=$(az webapp config appsettings list -g csnhc-ai -n TicketTicket \
  --query "[?name=='DIRECT_URL'].value | [0]" -o tsv)
cd apps/api
DATABASE_URL="$PROD" DIRECT_URL="$PROD" npx prisma migrate status   # KEEP THIS
```

**Save that output.** With three migrations pending it is the only rollback
reference that will exist.

### Step 2 — Apply migrations 55, 56, 57

```bash
DATABASE_URL="$PROD" DIRECT_URL="$PROD" npx prisma migrate deploy
DATABASE_URL="$PROD" DIRECT_URL="$PROD" npx prisma migrate status   # expect 57
```

- **`DIRECT_URL` is port 5432.** The 6543 pooler **cannot run migrations at all**.
- Expect **exactly three** pending: `ticket_links`,
  `notification_type_ticket_created`, `canned_response_actions`. **If the list
  differs, stop and report** — that means the schema is somewhere unexpected.
- Two of the three add an **enum value** and deliberately do not use it; the code
  starts using them after the app deploys. That ordering is intentional.

### Step 3 — Build and push

1. **Kill stray node processes.** Repo-scoped filter in `repo-landmines.md` — and
   note its caveat: **it misses a dev server started with a relative path**, so
   check the listening ports too.
2. **Build** with `create-deploy-zip.ps1`. **Rebuild is required.**
3. **Push:**

   ```bash
   az webapp deploy -g csnhc-ai -n TicketTicket --type zip --async true --src-path <zip>
   ```

   **Do NOT run `deploy-to-azure.ps1`** — `docs/DEPLOYMENT.md:38` forbids it.
   **Never push to the `azure` git remote.**

## 5. Post-deploy checks

**Ordered by what it costs to get wrong.**

1. **Schema.** `migrate status` → **57**, and the **six trigram GIN indexes still
   present**. Three migrations at once makes this the most important check here.
2. **Commit landed.** Deployed asset hash matches the package you built.
3. ⚠️ **An internal note still sends no email.** Post one and confirm. If an email
   arrives, **stop and report** — highest-consequence failure in this subsystem.
4. ⚠️ **A public reply still sends exactly one email, threaded.** Post two replies
   on the same ticket; both must land in **one** email conversation.
5. **Staff stop getting email.** Assign a ticket, transfer it, change its status to
   something other than Resolved. **No email for any of them**, and the assignee
   still gets the **bell** each time. Both halves.
6. **The new "ticket arrived" bell.** Create a ticket in a department you are on.
   The team should be belled. **This is new** and it replaces an email that used to
   be the only signal.
7. **Resolved still emails the requester**, with confirm / reopen / **how did we
   do?**
8. **The two production defects are fixed** — click **Insert template** in the
   composer (it should open the picker; it currently does nothing), and confirm a
   template's placeholders fill in a **name** rather than a blank.
9. **Create a template (1.7b), as the owner.** New → name, content, an action or
   two, share with your team → save. Then apply it: one click should fill the
   composer and set the status and tag.
10. **Link two tickets (1.6).** Confirm the link shows on both, and that a parent
    lists its children.
11. **Container log** after a few minutes: no repeating error, nothing unexpected
    from the scheduler or the outbox sweeper.

### ❌ What cannot be checked, and do not try

**Anything needing a reply to arrive by email.** No mailbox feeds the webhook, so
cards 1.29 and 1.40 stay unverified in production. Their checks live on **card
1.24's checklist**. Do **not** fabricate a webhook call against production to
simulate it — that writes a real ticket somebody then has to delete.

## 6. Known and deliberate — do not "fix" these

- **SLA alerts no longer email anyone**, including on-call addresses. Owner's
  decision, deliberate. In-app only.
- **An unrouted inbound ticket reaches nobody** — no email, no bell — because the
  bell goes to the assigned team and an unrouted ticket has none. Known, on card
  1.24's checklist.
- **A macro cannot send email or notify.** Enforced on save and on execute.
- **A looped-in EMPLOYEE can reply by email but cannot open the ticket.** Card
  1.36's rule; intended.
- **`EMAIL_COMPANY_NAME` is now unread** — it only ever appeared in the deleted
  sign-offs.
- **`e2e/` is untracked on purpose.** Leave it out of the package.
