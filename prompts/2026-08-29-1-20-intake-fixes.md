## 3. Facts established first (verified 2026-08-29 by the planning session)

### Defect A — idempotency is inert for anonymous callers

| Fact | Consequence |
|---|---|
| `common/idempotency.interceptor.ts:161-182` `resolveActorScope()`: an authenticated request scopes by `request.user.id`; an anonymous one builds a SHA-256 digest of `[request.ip, firstValueOf(x-forwarded-for), user-agent, x-attachment-scan-secret, x-inbound-email-secret, x-intake-secret].join('|')`. | The scope is only as stable as its inputs. |
| **Azure App Service sets `X-Forwarded-For` to `ip:port`, and the source port changes on every new TCP connection.** Deploy agent proved it both ways in production: two connections → two different `actorId` values → **two tickets**; one reused connection → same scope → `Idempotency-Replayed: true`. | The mandatory `Idempotency-Key` (card 1.19 §4.2) does nothing across connections. A Power Automate retry duplicates the ticket. |
| The interceptor is registered globally (`app.module.ts:124-127`, `APP_INTERCEPTOR`). | The controller comment calling it "opt-in" is wrong about *registration* — it is opt-in only in the sense that it no-ops without an `Idempotency-Key` header. Fix the comment while you are here. |
| A caller presenting a correct shared secret has already identified itself; the IP adds nothing but instability. | When a recognised secret header is present, scope by **the secret**, not the network. |

### Defect B — intake cannot create IT tickets

| Fact | Consequence |
|---|---|
| Production has exactly one custom field: **`"Asset Tag"` (TEXT), `isRequired: true`, `teamId = it-service-desk`, no category.** (Verified directly against the production database.) | Only IT is affected today; the other five departments work. |
| `custom-fields.service.ts:400-412` loads fields where `(teamId IS NULL OR teamId = <ticket team>) AND (categoryId IS NULL OR categoryId = <ticket category>)` and throws `BadRequestException('Required custom field "X" must be provided')` when a required one is missing or blank. | Intake to `it-service-desk` **always** 400s. |
| `CreateTicketDto` accepts `customFieldValues?: [{ customFieldId: uuid, value?: string }]`; `CreateIntakeTicketDto` has no equivalent. | The intake service cannot supply one. Add a field-**name**-keyed map so a flow never handles UUIDs. |

## 4. Decisions and assumptions

1. **Scope anonymous idempotency by the secret, not the network.** In `resolveActorScope`, if any of the three secret headers is non-empty, return `anonymous:` + SHA-256 of `[<header name>, <header value>].join('|')` — stable for as long as that secret lives, and different per integration. Only when **no** secret header is present, fall back to the current network seed **with the port stripped** from both `request.ip` and the first `X-Forwarded-For` entry (`replace(/:\d+$/, '')`, IPv6-safe: only strip when the remainder still parses as an address — simplest correct rule: strip a trailing `:digits` only if the string contains a `.` (IPv4) or is bracketed `[...]:port`).
2. **Rotating a secret invalidates in-flight keys** for that integration. Acceptable and correct; document it next to the seed comment.
3. **`customFields` on the intake DTO:** `Record<string, string>`, at most 20 entries, each key ≤ 100 chars and value ≤ 5000. Keys are custom-field **names**, matched case-insensitively and trimmed against the fields applicable to the resolved team/category.
4. **Unknown field name → 400** naming it and listing the applicable field names. **Missing required field → 400** listing the required names for that department — so a flow builder discovers them the same way they discover department slugs (from the error), without reading code.
5. **No schema change**, no new endpoint, no change to how the web creates tickets.

### Task 1 — Fix the idempotency scope (defect A)

**Files:** Modify `apps/api/src/common/idempotency.interceptor.ts`; Create `apps/api/src/common/idempotency.interceptor.spec.ts` (or extend if one exists)

- [ ] Replace `resolveActorScope` with:

```ts
  /**
   * Idempotency scope for the caller. Authenticated requests scope by user id.
   *
   * A caller presenting a shared secret has already identified itself, so the
   * scope is derived from THAT — never from the network. Azure App Service sets
   * X-Forwarded-For to `ip:port` with a fresh source port per TCP connection, so
   * a network-derived scope changes between retries and the replay never fires
   * (proved in production 2026-08-28: two connections, two tickets).
   *
   * Rotating a secret deliberately invalidates that integration's in-flight keys.
   */
  private resolveActorScope(request: Request & AuthRequest) {
    if (request.user?.id) {
      return request.user.id;
    }
    for (const header of SECRET_SCOPE_HEADERS) {
      const value = this.readHeaderValue(request.headers[header]).trim();
      if (value) {
        return `anonymous:${this.digest([header, value])}`;
      }
    }
    const forwardedFor = stripPort(
      this.readHeaderValue(request.headers['x-forwarded-for']).split(',')[0]?.trim() ?? '',
    );
    return `anonymous:${this.digest([
      stripPort(request.ip ?? ''),
      forwardedFor,
      this.readHeaderValue(request.headers['user-agent']),
    ])}`;
  }

  private digest(parts: string[]): string {
    return createHash('sha256').update(parts.join('|')).digest('hex').slice(0, 24);
  }
```

      with, above the class:

```ts
/** Shared-secret headers that identify an integration caller, in priority order. */
const SECRET_SCOPE_HEADERS = [
  'x-intake-secret',
  'x-inbound-email-secret',
  'x-attachment-scan-secret',
] as const;
```

      and `stripPort` as a one-export helper in a new `apps/api/src/common/strip-port.util.ts`:

```ts
/**
 * Remove a trailing `:port` from an address. Azure App Service writes
 * `X-Forwarded-For: 1.2.3.4:56789`. IPv6 keeps its colons unless bracketed.
 */
export function stripPort(address: string): string {
  const bracketed = /^\[.+\]:\d+$/.exec(address);
  if (bracketed) {
    return address.slice(0, address.lastIndexOf(':'));
  }
  if (address.includes('.') && /:\d+$/.test(address)) {
    return address.replace(/:\d+$/, '');
  }
  return address;
}
```

## 7. Security considerations

- Scoping by the secret means **two callers sharing a secret share an idempotency scope**. That is correct — they are the same integration. Give each integration its own secret when card 2.6 (API keys) lands.
- The secret is hashed into the scope, never stored raw: `IdempotencyRequest.actorId` holds only a 24-character digest. Verify that in the test — the raw secret must not appear in that column.
- The error messages list custom-field **names** and department slugs to a caller that already holds the shared secret. Same trust level as the existing department-slug listing. Do not include field *values* or ids.
- Stripping the port does not weaken the fallback scope: the client IP is still there, and that path is only reached by a caller with no secret at all.
