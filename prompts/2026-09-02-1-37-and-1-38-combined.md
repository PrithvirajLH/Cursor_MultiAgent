## 1. The three faults

| | Fault | Where |
|---|---|---|
| **A** | On an **unassigned** ticket the composer offers `Public`, the server stores `INTERNAL`, and the app says **"Reply sent"** | `TicketDetailPage.tsx:383` |
| **B** | An author's **own** internal note renders in the ordinary blue "sent" bubble — the amber treatment is unreachable for it | `TicketConversation.tsx:341` |
| **C** | Only the **first** message of a grouped run carries the `Internal` badge | `TicketConversation.tsx:298` |

Proven in the browser on 2026-09-02, dev ticket `IS_20260609_002` (unassigned, IT
Service Desk) as `agent@company.com`:

```
20:14:50  INTERNAL  agent@company.com   Public reply from the agent - this one shoul…
20:15:22  INTERNAL  agent@company.com   Internal note one - this must NOT reach the …
20:15:30  INTERNAL  agent@company.com   now ?
20:15:38  INTERNAL  agent@company.com   Test 4
```

`outbox rows for this ticket: 0`. The first was typed with the toggle plainly
reading `Public`. Then, bypassing the UI:
`curl -d '{"type":"PUBLIC"}'` → `{"type":"INTERNAL"}`, **201**.

Viewed as a **different** user the same six messages render amber under a
**single** `Internal` badge. Viewed as the **author**: all blue, one badge.

## 2. The owner's decision — the API is right, the screen is wrong

The two layers disagreed about unassigned tickets:

| Layer | On an unassigned ticket |
|---|---|
| **API** `access-control.service.ts:215` — `assigneeId === user.id` | `null` never equals a user id → **peer agent** → force `INTERNAL` |
| **Web** `TicketDetailPage.tsx:383` — `if (!ticket.assignee) return false` | → **not** a peer agent → shows the toggle |

**Owner's ruling (2026-09-02): an agent must assign the ticket to themselves
before they can reply to the requester.** Replies stay tied to an owner.

So **the API keeps its current behaviour and needs no change.** The web must stop
offering an option the server will refuse. A useful side effect: the comment at
`tickets.service.ts:1524` claiming *"the UI also hides the toggle"* — currently
false in this exact case — **becomes true**. Leave that comment alone; do not
delete it.

**Applies to `AGENT` only.** `isPeerAgent` returns `false` immediately for any
other role, so LEAD, TEAM_ADMIN and OWNER continue to reply publicly on
unassigned tickets. Do **not** widen the rule.

**Files:** `apps/web/src/pages/TicketDetailPage.tsx`

Do this **first** and independently of the rest. Even with Task 2 in place the
override can still fire — an agent opens an assigned ticket, starts typing a
public reply, and someone reassigns it before they hit send. This is the only

The client already has the truth and uses it in one place out of three:

| Line | Today |

| `:1460` | realtime event **does** use `serverMessage.type` ✅ |
