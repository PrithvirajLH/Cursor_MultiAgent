# Implementation Prompt — 1.69 the rate limit is one global bucket

**Date:** 2026-09-10
**Repo:** `Ticketing System Quality Review` (branch `ui-redesign-and-api-hardening`)
**Card:** 1.69 — **one card, four steps, in this order**

**One commit per step. Four commits.** Work straight through. Do not check in
between steps, and do not ask permission.

> ## This is live, not latent
>
> **288 requests were refused with `429` in production today**, every one of them
> `/api/tickets`. The volume is still climbing. **The owner is being told
> "Couldn't load list" by their own server, and the server is telling the truth.**

---

## The diagnosis, already done — do not re-derive it

- The limit is the **code default: 120 requests per 60 seconds**
  (`app.module.ts:62`). **Nothing overrides it in production** — there is no
  `RATE_LIMIT_*` app setting.
- The `ThrottlerModule` config (`app.module.ts:53-66`) supplies `name`, `ttl`,
  `limit` and `setHeaders` — and **no `getTracker`.** So
  `route-throttler.guard.ts:55` forwards `this.commonOptions.getTracker!`, a
  non-null assertion on something never set, and the library default applies:
  **`req.ip`.**
- ⚠️ **There is no `trust proxy` anywhere**, so `req.ip` is the immediate peer —
  the App Service ingress. **All 1,640 production requests log the same
  `remoteAddress: 169.254.131.5`.**

**So it is one bucket for the entire application** — every user, every device,
plus the platform's own health probe. **This is why the IP fallback in step 2 is
worthless and must not be relied on.**

Measured today: **1,628 requests to `/api/tickets`, 956 of them `pageSize=1`
count queries, 268 presence pings, 288 × 429.**

## Step 1 — raise the limit (owner action, no code, no deploy)

**Do this first because it is the only relief available today**, and it needs
nothing but a setting.

```
az webapp config appsettings set --name TicketTicket --resource-group csnhc-ai \
  --settings RATE_LIMIT_LIMIT=1200
```

- [ ] ⚠️ **This is a mitigation, not the fix.** One bucket at 1,200/min is still
      one bucket — it buys room while steps 2–4 land. **Say so in your report** so
      nobody closes the card here.
- [ ] **An app-settings change restarts the App Service**, so expect a cold start.
- [ ] ⚠️ **The planner cannot run this** — Azure resource writes are blocked from
      agent sessions here. **The owner runs it.** If it is already raised when you
      start, note the value and move on.

## Step 2 — key the throttle on the user (the actual fix)

- [ ] **Add a `getTracker` to the `ThrottlerModule` config** that returns the
      authenticated user's id, so each person gets their own budget.
- [ ] ⚠️ **VERIFY THE GUARD ORDER BEFORE YOU TRUST `request.user`. This is the
      one thing that decides the design.** There are **two** global `APP_GUARD`
      providers: `AuthGuard` (`auth/auth.module.ts:10`, in an imported module) and
      `RouteThrottlerGuard` (`app.module.ts:136`, in the root module's own
      providers). NestJS does **not** strictly guarantee ordering across modules.
      **If the throttler runs first, `request.user` is undefined and a naive
      tracker silently keys everyone into one bucket again — looking fixed and
      changing nothing.**
- [ ] **So prove it, don't assume it:** log what the tracker actually receives on
      one real request before building on it. **Report what you found.**
- [ ] **If `request.user` is not available**, the robust fallback is the **bearer
      token's `sub`/`oid` claim, read without verification, for bucketing only.**
      ⚠️ **Say explicitly in a comment that it is not used for authorization** —
      an unverified claim is fine for choosing a bucket (forging one only gets you
      your own) and catastrophic for deciding access. **A hash of the whole token
      also works** but changes on every refresh, giving one person a fresh budget
      each hour; note that trade-off if you choose it.
- [ ] **Keep an IP fallback for genuinely anonymous routes** — the email-action
      links (card 1.44) and the inbound webhook are `@Public()` and have no user.
      ⚠️ **But do not present it as a safety net for signed-in traffic: it
      collapses to a single bucket, as measured above.**
- [ ] ⚠️ **`route-throttler.guard.ts:55-56` will need revisiting**, since both
      `getTracker!` and `generateKey!` are asserted non-null there. Once a real
      `getTracker` exists the first assertion becomes true — **check the second
      one too rather than leaving a lie next to a fixed line.**

### Tests

- [ ] **Two different users get separate budgets** — the regression assertion, and
      the whole point of the card.
- [ ] **The same user from two IPs shares one budget.**
- [ ] **An anonymous request still gets limited** via the fallback.
- [ ] ⚠️ **A request where the tracker cannot identify a user does NOT silently

## Step 3 — exempt the health probe

**`/api/health` is not throttle-exempt**, and the platform probes it about once a
minute. In a quiet window it was **essentially all the traffic**, spending from
the same bucket as real users.

- [ ] **Add `@SkipThrottle()`** to the health controller.
- [ ] ⚠️ **Check whether anything else unauthenticated is in the same position** —
      the readiness endpoint (card 0.5), the inbound webhook, and card 1.44's
      email-action routes. **Say which you exempted and which you deliberately did
      not.** The webhook and the email links **should stay limited**; they are
      write paths reachable from outside.

## Step 4 — stop the count storm, using the endpoint that already exists

**✅ Do not build a batched count endpoint. There is one.**

`GET /api/tickets/counts` (`tickets.controller.ts:86` → `getCounts`,
`tickets.service.ts:714`) already returns **ten counts in a single call** —
`assignedToMe, triage, open, unassigned, resolved, resolvedByMe,
createdByMeOpen, createdByMeResolved, atRisk, overdue` — and it is **cached per
user** (`CACHE_SUMMARY_TTL_MS`, default 45s).

**`App.tsx:535` already uses it** through `useTicketCountsQuery`. **The sidebar
does not** — it fires ~11 separate `GET /tickets?pageSize=1` calls through
`useViewCounts`, uncached.

- [ ] **So this step is consolidation, not construction:** move the sidebar's
      badges onto the existing cached endpoint.
- [ ] **Some badges are already covered** — *Assigned to Me*, *Unassigned*,
      *Breach risk* and the resolved counts map onto fields that exist. **Others
      are not**: *SEV1 today*, *Awaiting reply > 24h*, *Watching*, *Mentions*,
      *Follow-ups*, *Reopened*. **Extend `getCounts` for those rather than leaving
      a second mechanism for the remainder** — a partial migration leaves both
      systems alive, which is the worst outcome.
- [ ] ⚠️ **This is the "second definition of what needs attention" problem that
      cards 1.16 and 1.53 both flagged.** Two count systems already disagree in
      principle; 1.65's implementer hit it directly when a nav badge kept showing
      a stale number because it came from the other source. **Finishing this
      retires that whole class.**
- [ ] ⚠️ **Every count must go through the same access filter as `/tickets`.** A
      batched count endpoint that takes filters and bypasses `roleFilter` is a
      data-exfiltration oracle — someone could count tickets they cannot read.
      `getCounts` already does this correctly; **keep it that way** and do not add
      a variant that accepts arbitrary client-supplied filters.
- [ ] **Team saved views (card 1.53) still need per-view counts**, and those are
      genuinely dynamic. **Do not break them.** If they must stay as individual
      queries, say so and say why — the win is removing the eleven fixed ones, not
      all of them.

### Tests

- [ ] **The sidebar issues ONE count request, not eleven.** That is the
      regression assertion — assert the call count, because a partial migration
      passes every other test.
- [ ] Every badge shows the same number it did before. **Pin a few explicitly**;
      a consolidation that quietly changes a count is worse than the storm.
