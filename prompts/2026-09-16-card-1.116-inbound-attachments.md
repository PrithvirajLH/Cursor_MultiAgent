# Card 1.116 — inbound email attachments have never been fetched

**Date:** 2026-09-16
**Repo:** `Ticketing System Quality Review` (branch `ui-redesign-and-api-hardening`)
**Found by:** the owner, replying to a real ticket with three images.

---

## In plain English

When the system checks the mailbox, it only asks Microsoft for the **words** in
each email. It never asks for the **pictures**. So every image anyone has ever
emailed to the service desk was left behind in the mailbox — not blocked, not
too big, not rejected. Never requested.

The owner's reply had three images. None arrived. The typed text looked missing
too, because the only thing above the signature was a pasted image, and a
dropped image leaves nothing behind.

Nothing is lost. The images are still in the mailbox.

---

## 1 — What is wrong

✅ **Measured against the owner's real email, 2026-09-16:**

```
The worker's query   →  hasAttachments: True,  attachments key: ABSENT
The same message     →  3 attachments:
                          image.png        212 KB   inline=true   (pasted)
                          aginf.png        4.36 MB  inline=false
                          Back Injury.png  4.34 MB  inline=false
```

`graph-mail.http-client.ts:73` fetches:

```
/mailFolders/inbox/messages/delta?$top=PAGE_SIZE
```

`attachments` is a navigation property. A delta query does not return it, and
`$expand` is not supported on delta. So `toMessage` (`:187`) reads
`item.attachments` → `undefined`, `toAttachments` returns `[]`, and
`inbound-mailbox.service.ts:367` maps an empty list into the ingest DTO.

**There is no separate attachment fetch anywhere in the poller.**

⚠️ **THIS IS A GAP, NOT A REGRESSION.** It has never worked. Both
`inbound-mailbox.service.spec.ts:25` and `test/integration/inbound-mailbox.spec.ts:54`
hardcode `attachments: []` in their fixtures, so the suite is silent on it and
always has been. Nothing in `docs/` acknowledges the limitation.

⚠️ **EVERYTHING DOWNSTREAM IS CORRECT AND STARVING.** The normalizer at
`inbound-email.service.ts:738`, card 1.105's per-file rejection reasons, the
`INBOUND_ATTACHMENTS_DROPPED` event, card 1.83's internal-note rule, blob
storage and the scan gate are all fine. None of them has ever run on a real
file, because nothing reaches them.

---

## 2 — The second bug, which would otherwise hide the first fix

⚠️ **`inbound-email.service.ts:792` DEMANDS AN EXACT BYTE MATCH:**

```ts
if (buffer.length !== declaredSize) {
  throw new BadRequestException(`expected ${declaredSize} bytes, got ${buffer.length}`);
}
```

The poller passes Graph's `size` (`inbound-mailbox.service.ts:370`,
`sizeBytes: attachment.sizeBytes || 1`). **Graph's `size` is the wire size —
base64 and MIME overhead included — not the decoded length.** They never match.

So fixing only the fetch produces zero attachments and a confusing reason.

✅ **THE CHECK IS RIGHT AND THE CALLER IS WRONG.** `sizeBytes` in the DTO means
"the size of the file I am handing you", and the poller was passing the size of
the envelope. **Fix the caller, not the check** — the check still protects the
relay path from a truncated download, and weakening it would weaken card 1.105
for a caller that is behaving correctly.

---

## 3 — The decision: how to fetch

**Chosen: per-message fetch, metadata first. NOT `$expand` on the delta page.**

| | `$expand` on delta | Per-message fetch ✅ |
|---|---|---|
| Downloads junk mail's files | Yes — before the not-addressed-to-us filter at `:253` | No |
| Downloads files it will reject | Always | No — size known from metadata first |
| Peak memory | A whole page as one JSON string | One attachment at a time |
| Blast radius of a failure | The **page** | One message |

⚠️ **THE DECIDING ARGUMENT IS THE POISON-PAGE LOOP.** With `$expand`, one page
that times out or exhausts memory means the delta cursor never advances, so the
next poll fetches the identical page and fails identically — and **no mail at
all** gets in until somebody notices. This repo has already been bitten by that
exact shape one level down: the comment on `normalizeInboundEmailAttachments`
records card 1.105's bug as *"the message stayed in the Inbox and was re-offered
every thirty seconds, failing identically each time."*

Secondary: the owner's one email is ~8.9 MB, ~11.9 MB once base64'd, and a page
is 50 messages.

⚠️ `$expand` on a delta query is believed unsupported by Graph outright, which
would make it moot rather than merely worse. Not relied on — the argument above
stands either way.

## 4 — The fix

- [ ] **`GraphMailMessage` carries `hasAttachments`** (delta does return it) and
      **drops `attachments`**, which is structurally always empty. Leaving a
      field that can never be populated is what hid this for so long.
- [ ] **Two new client methods**, both on the `GraphMailClient` seam so the
      whole thing stays testable without Graph:
      `listAttachments(mailbox, messageId)` → metadata only
      (`$select=id,name,contentType,size,isInline`, no content), and
      `fetchAttachmentContent(mailbox, messageId, attachmentId)` → base64.
- [ ] **Fetch only after the addressing check passes**, inside `handleMessage`,
      so mail that is not ours never costs a download.
- [ ] ⚠️ **`sizeBytes` becomes the DECODED length** — the caller's contract.
      The `|| 1` fallback goes with it.
- [ ] ⚠️ **AN ATTACHMENT FAILURE MUST NEVER LOSE THE EMAIL.** A failed content
      fetch emits the entry with no content, so the existing normalizer rejects
      it and card 1.105's `INBOUND_ATTACHMENTS_DROPPED` event names the file on
      the ticket. Reusing that path rather than adding a second one.
- [ ] **Content is fetched for at most `INBOUND_EMAIL_MAX_ATTACHMENTS` files**;
      the rest are passed without content so the normalizer reports the overflow
      in its own words.

### The signature-logo rule — the owner's decision

⚠️ **OWNER'S CALL, 2026-09-16: "dont pull signature logos."**

An Outlook signature logo is an inline image, and so is a deliberately pasted
screenshot. The discriminator is **size**: logos are a few KB, the owner's
pasted image was 212 KB.

- [ ] **Skip an attachment when it is inline AND an image AND smaller than
      `INBOUND_INLINE_IMAGE_MIN_BYTES` (default 50 KB).**
- [ ] ⚠️ **NON-INLINE FILES ARE NEVER SKIPPED, whatever their size.** Somebody
      deliberately attaching a small file means to attach it.
- [ ] Kept as a leaf util so the rule is written once and testable.
- [ ] **The known cost, accepted:** a genuinely tiny pasted screenshot under
      50 KB is skipped. The threshold is configurable for that reason.

## 5 — Tests

- [ ] **An email with two real attachments and a signature logo ingests two
      files.** The assertion the card exists for.
- [ ] **The pasted 212 KB inline image IS kept** — inline is not the same as
      junk.
- [ ] **A 6 KB inline logo is skipped.**
- [ ] **A small NON-inline file is kept** (non-vacuity for the rule's shape).
- [ ] **`hasAttachments: false` makes no Graph call at all** — non-vacuity for
      the whole path.
- [ ] **Mail that is not addressed to us makes no attachment call.**
- [ ] **A failing content fetch still ingests the email**, and the file is
      recorded as dropped.
- [ ] **`sizeBytes` is the decoded length**, so the normalizer's equality check
      passes — the regression assertion for §2.

---

## 6 — What this does not cover

- **Attachments over Graph's inline-content limit.** Very large files need
  `/$value` or a chunked session. Out of scope: `ATTACHMENTS_MAX_MB` is 10 and
  such files are rejected anyway — but rejected for the right reason now.
- **Re-linking a pasted image into the message body.** The image will arrive as
  an attachment; the body still loses the `<img>` in the HTML→text conversion.
  Making the body reference the stored file is a separate card.
- **The mail already sitting in the mailbox.** The delta cursor has moved past
  it. Re-ingesting history is a separate operational decision.
