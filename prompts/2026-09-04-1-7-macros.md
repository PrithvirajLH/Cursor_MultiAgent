## 2. ⚠️ The action allowlist — the most important decision in this card

**A macro must NOT be allowed every action the rule engine supports.** Three of the
twelve are dangerous in one click, and one of them undoes work landing this week:

| Action | Macro? | Why |
|---|---|---|
| `set_status`, `set_priority`, `set_category` | **Yes** | The point of the card |
| `add_tag`, `remove_tag` | **Yes** | The point of the card |
| `assign_user`, `assign_team` | **Yes** | The point of the card |
| `add_follower` | **Yes** | Harmless and useful |
| **`send_email`** | **NO** | A one-click button that emails an arbitrary address. **Card 1.42 is removing most email precisely to stop noise**; a macro that sends email reintroduces it through a side door. |
| **`notify_requester`** | **NO** | Same, and it would reach a requester with no agent reading what went out |
| **`notify_team_lead`** | **NO** | Same |
| `add_internal_note` | **Owner's call** | Defensible — a macro that records "standard password reset performed" is useful. But it writes into the conversation, so **say what you chose** |

- [ ] Enforce the allowlist **server-side**, on save **and** on execute. A macro
      saved before the allowlist existed, or edited through a stale client, must
      not execute a forbidden action.
- [ ] The allowlist lives in **one** constant, next to the executor, so the next
      person adding an automation action has to decide consciously whether a macro
      may use it.

## 3. ⚠️ `executeActions` is private and coupled to automation rules

The card says it depends on "1.4's shared action executor". **It is not shared.**
Its real signature is:

```ts
private async executeActions(
  tx: Prisma.TransactionClient,
  ticketId: string,
  actions: ActionNode[],
  ticket: ActionTicket,
  ruleId: string,
  ruleCreatedById: string,
): Promise<{ current: ActionTicket; postCommit: PostCommitTask[] }>
```

Two problems:

1. **It takes `ruleId` and `ruleCreatedById`.** A macro run by a human is not a
   rule firing. `AutomationExecution` rows are per-ticket and drive automation
   reporting — **writing them with a fabricated ruleId would corrupt that
   reporting** and make a person's click look like a rule.
2. **It takes a transaction client and returns post-commit tasks**, so whoever
   calls it owns the transaction and must run the tasks after commit. Get that
   wrong and a macro half-applies.

**Decide and say which you did:**

- **(a) Extract** the action switch into a shared executor that takes an explicit
  **provenance** (`{ kind: 'rule', ruleId } | { kind: 'macro', cannedResponseId, actorId }`)
  instead of a bare `ruleId`. Correct long-term. **Riskier** — this is live
  automation code. Only acceptable if the existing automation tests pass
  **untouched**; if you find yourself editing them to fit the refactor, stop.
- **(b) Have the macro path call the ticket-service methods directly** for the
  allowlisted subset. Smaller and safer, but it is a second copy of the switch —
  the thing that caused 1.36's Fault C and 1.38.

**My recommendation: (a), with the provenance parameter**, precisely because (b)
duplicates a rule that will drift. But **stop and report** if the extraction cannot
be done without changing automation behaviour or its tests.

Either way: **the audit trail must show a human ran a macro**, not that a rule
fired. Say where that lands.

## 7. Acceptance criteria

1. A "Password reset done" macro pastes a personalised reply, sets **Resolved** and
   adds tag `password` in one click.
2. **A macro cannot send email or notify anyone**, on save or on execute.
3. An unknown placeholder produces nothing, never a raw `{{...}}`.
4. Substitution is not recursive and cannot be injected through a display name.
5. A macro respects `canWriteTicket` and card 1.38's public/internal rule.
6. The audit trail shows a person ran a macro, not that a rule fired.
7. The existing automation tests pass untouched.
8. Migration additive, **0 DROPs**, dev before production.
9. Both `tsc` clean; unit, integration and vitest at or above §6.
