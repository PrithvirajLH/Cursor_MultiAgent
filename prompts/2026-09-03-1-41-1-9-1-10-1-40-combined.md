## 1.9 — "Someone is already on this" (S, API + web)

**Card:** the `### 1.9` section of the master plan.

Two agents answering the same requester is the classic embarrassment.

**The whole point is that this is a clone, not a new subsystem.** Copy the typing
plumbing:

- `POST /api/tickets/:id/viewing { isViewing }`, DTO cloned from
  `tickets/dto/ticket-typing.dto.ts`
- `RealtimeService` event `ticket.viewing`, emitted **to the same audience as
  `ticket.typing`** (`ticket-realtime.service.ts`)
- `TicketDetailPage` sends `true` on mount, heartbeats every **30 s**, sends
  `false` on unmount

⚠️ **The audience is a security boundary, not a convenience.** `ticket.typing`
already goes only to people who may see the ticket. **Reuse that audience
exactly.** Inventing a broader one would tell people a ticket exists — and who is
looking at it — when they cannot open it. Cards 1.36 and 1.38 were both this
mistake in other forms.

- [ ] Presence must **expire**. A closed laptop must not leave a phantom viewer
      forever; the heartbeat interval is what makes staleness detectable, so pick
      a timeout and say what it is.
- [ ] Do not show the current user as a viewer of the ticket they are on.
- [ ] **Done when:** an e2e case in `e2e/realtime-chat.spec.ts` shows the banner to
      agent B when agent A opens the ticket. Note `e2e/` is **untracked on
      purpose** — leave it that way.

## 1.10 — Snooze / follow-up date (S, API + web + **migration 54**)

**Card:** the `### 1.10` section of the master plan. Depends on 1.1 and 1.3, both
**live**.

"Remind me Friday." Today a ticket waiting on a vendor relies on somebody
remembering.

- `Ticket.followUpAt DateTime?` + an index
- Set through card 1.1's existing `PATCH` — **do not add an endpoint**
- The card 1.3 scheduler fires an in-app notification when due **and clears the
  field**
- Sidebar row with a date picker; saved-view preset "Follow-ups due today"; a list
  badge when overdue

### The migration — read this before writing it

It needs **two** additive things: the column + index, and a new
`NotificationType` value `FOLLOW_UP_DUE`.

- [ ] **Hand-write it.** `prisma migrate diff` will also emit the standing twelve
      destructive statements — six trigram `DROP INDEX` and six `ALTER COLUMN …
      DROP DEFAULT`. **Remove every one and document them in the file**, exactly as
      migrations 52 and 53 do.
- [ ] `grep -cE '^(DROP|ALTER TABLE .* DROP)' migration.sql` must be **0**.
- [ ] **The enum addition has precedent — copy it.**
      `20260828120000_ticket_channel_api/migration.sql` is a one-liner:
      `ALTER TYPE "TicketChannel" ADD VALUE 'API';`. Do the same for
      `NotificationType`.
- [ ] ⚠️ **Postgres will not let a newly added enum value be *used* in the same
      transaction that adds it.** So the migration may **only add** the value —
      do not seed or backfill any row using `FOLLOW_UP_DUE` in migration 54. If
      you find yourself wanting to, **stop and report**.
- [ ] **Apply to local-dev Supabase first, then production.** It will be migration
      **54**.
- [ ] The notification must respect who may see the ticket. It goes to the
      **assignee**; if the ticket has none, say what you did rather than guessing.

## 1.40 — A looped-in person's reply is refused and lost (S–M, API)

**Card:** `prompts/2026-09-03-1-40-a-looped-in-reply-is-refused.md`

A colleague we CC'd replies to the thread and the system answers **403 and stores
nothing**. Nobody is told.

### The §4 decisions — settled here so you are not blocked

The card says not to start until §4.1 is decided. **These are my calls, not the
owner's**, and the owner can overrule any of them:

1. **Who may reply: anyone we actually emailed** — the requester, the assignee,
   and the ticket's **followers**, which is exactly the `Cc` list card 1.33 sends
   to and card 1.28 displays. **Not "any EMPLOYEE"**, which would let anyone who
   guesses a reply address post to any ticket.
2. ⚠️ **The reply token must not become the authorisation.** The inbound address
   carries `+ticket-<id>`, which is a **bearer token every thread participant can
   read and forward**. It says *which ticket*. It must never say *who may write*.
   Match the **sender** against the audience.
3. **A sender in no relationship to the ticket: record a ticket event, do not
   store the body.** An agent learning "someone outside the thread replied" is
   useful; silently ingesting mail from anyone who can guess an address is not.
   **This is the one most worth the owner's opinion** — flag it in your report.
4. **Replying makes you a follower**, so you get the rest of the thread. Say so
   explicitly in code, because it changes who receives subsequent mail.
5. **Check whether a schema change is needed before assuming one is.** The audience
   already exists in `TicketFollower`. If you reach for a column, **stop and
   report**.

### Two things carried from cards 1.29 and 1.36

- [ ] **Keep the message-before-status ordering** that `4acca6d` established.
      *A status derived from a message must not outlive the message* — that comment
      is in `inbound-email.service.ts` and is load-bearing.
- [ ] A third party's reply must stay `PUBLIC` and **must not** grant them sight of
      internal notes. Card 1.36's read filter governs that; do not touch it.
- [ ] Put the rule in **`AccessControlService`**, not inline in the inbound
      service. The visibility rule already lives in three places there; a fourth
      copy in a different file is how 1.36's Fault C and 1.38 happened.
