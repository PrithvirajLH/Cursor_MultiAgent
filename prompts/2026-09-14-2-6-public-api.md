## 1 — Two decisions, settled here so you do not stall

### ⚠️ Decision one: what goes in a webhook payload

**The planner's recommendation, and the owner has not overridden it: IDs and
metadata only. Never message bodies, never descriptions, never custom-field
values.**

This is a healthcare desk. A ticket body can contain PHI, and a webhook sends it
to a third-party system nobody here controls, over a URL an admin typed. A
consumer that needs the content can call back with its key and be access-checked
on the way in.

- [ ] **Ship `ticket.created`, `ticket.status_changed`, `message.added` carrying
      ids, timestamps, status/priority, team and actor id.**
- [ ] ⚠️ **If you think a payload needs a body field, stop and ask.** Do not add
      one "for convenience" — it is the difference between a webhook and a data
      leak.
- [ ] **Version the envelope from day one** (`"version": 1`). Retrofitting a
      version onto a shipped webhook means breaking every consumer at once.

### ⚠️ Decision two: does the existing intake secret become an API key?

**There is already a machine-credential mechanism, and this card adds a second.**
`INTAKE_API_SECRET` — one shared secret, constant-time compared in
`intake.service.ts:56-75`, guarding `POST /api/tickets/intake`, which Power
Automate uses in production today.

**One rule answered in two places is the drift shape behind cards 1.36, 1.38,
1.47, 1.50, 1.61, 1.70, 1.71, 1.75 and 1.76 — eleven now.** So this needs an
explicit answer rather than an accident.

- [ ] ✅ **The planner's recommendation: build `ApiKey` first, leave intake alone
      in this card, and say in the code comment that intake is the one caller not
      yet migrated and why.** Migrating a live Power Automate integration is a
      coordinated change with the owner and does not belong in the same commit as
      the mechanism it moves to.
- [ ] ⚠️ **But note what it buys, because it is worth the owner's attention:
      migrating intake to an API key would RETIRE CARD 1.59.** That card — rotate
      the leaked intake secret — is deferred because rotation means a coordinated
      swap with Power Automate. **A per-caller revocable key makes rotation a
      button**, and the leaked value stops mattering the moment the key is
      revoked. **Say this in your report.**

- [ ] **Store a hash, never the key.** Show the key **once** at creation and never

## 4 — Commit three: outbound webhooks

```prisma
model WebhookSubscription {
  id        String   @id @default(uuid())
  url       String
  secret    String
  events    String[]
  isActive  Boolean  @default(true)
  createdAt DateTime @default(now())
}
```

✅ **Verified: no `WebhookSubscription` model exists today.**

### ⚠️ This is the part with a real security question: SSRF

**The server will make HTTP requests to a URL an admin typed.** In Azure that
includes reachable internal addresses — the instance metadata endpoint at
`169.254.169.254` being the obvious one, and card 1.69 already proved this app
sees `169.254.x.x` as its own ingress.

- [ ] ⚠️ **Validate the destination before ever calling it: HTTPS only, public
      hosts only, and reject loopback, link-local (`169.254.0.0/16`), and private
      ranges.** Reject at **save** time so an admin gets an error, **and** at
      **send** time so a DNS record that changes later cannot get through.
- [ ] ⚠️ **Do not follow redirects.** A permitted host that 302s to
      `169.254.169.254` defeats a save-time check entirely.
- [ ] **Stop and report if you cannot block those ranges cleanly** rather than
      shipping a best-effort filter.

### Delivery

- [ ] ⚠️ **Model it on `NotificationOutbox`. Do not invent a second retry
      mechanism.** That table already carries queued / sent / failed, retry and a
      dead state, and card 1.32 built the "a failed send does not vanish"
      behaviour on it. **A second, subtly different delivery pipeline is the
      twelfth instance of the shape this project keeps paying for.**
- [ ] **HMAC-SHA256 over the raw body, in a signature header**, with a timestamp
      so a captured call cannot be replayed.
- [ ] ⚠️ **The subscription `secret` is a credential in the database.** It must
      never appear in a log, in the admin screen after creation, or in the
      `/api/docs` example payloads.
- [ ] **Five retries with backoff, then a dead state** — and the dead state must
      be visible to an admin. A webhook that silently stopped delivering is worse
      than one that never worked.

### Tests

- [ ] ⚠️ **A URL pointing at `169.254.169.254`, `127.0.0.1` and a private range is
      rejected** — at save and at send. **The security assertion of this card.**
- [ ] **A consumer can verify the signature**, computed independently in the test
      rather than by calling the same helper the code uses. **A signature test
      that reuses the signing function proves only that the function is
      deterministic.**
- [ ] **A failed delivery retries and then goes dead**, and the dead row is
      visible.
- [ ] ⚠️ **No payload contains a message body, description or custom-field
      value.** Assert on the serialised payload, so adding a field later fails
      this test rather than quietly shipping PHI.
